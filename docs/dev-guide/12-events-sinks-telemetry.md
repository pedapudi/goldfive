# 12. Events, Sinks, and Telemetry

## Read this chapter when...

- You are adding a new event kind, or a new field to an existing event
  payload, and you need the additive-only proto workflow (`make proto`,
  `pb/` hygiene, fresh field numbers).
- You are writing or modifying an `EventSink` and need to know the
  DUAL-ENVELOPE contract (proto `Event` vs `make_event` dicts) and the
  `DESCRIPTOR` duck-typing every sink must honour.
- You are emitting telemetry from a detector, the steerer, or an
  executor and need the best-effort emit wrappers so an emit failure
  never touches control flow.
- You need to know exactly which `outcome` / `verdict_kind` / `reason`
  strings downstream consumers (harmonograf, zicato) join on — changing
  one silently breaks a consumer.
- You are debugging why an event did not reach a sink, or why a JSONL
  file has camelCase keys while a log line has snake_case keys.
- You are wiring decision telemetry (`SteeringDecisionMade`,
  `JudgementEmitted`, `ReasoningJudgeInvoked`, `PolicyApplied`,
  `LadderTransitionDecided`, `DetectorDispatchOrdered`,
  `RetryBudgetSpent`, `reasoning_judge_utility_summary`) and need the
  spec for each field.

## Invariants that bind you here

1. **Proto is the source of truth; field numbers are frozen forever.**
   Adding a field means a fresh, never-before-used tag number. Reusing a
   retired number (see `DriftDetected` field 11 `synthetic`, `reserved`
   in `events.proto`) corrupts every consumer that still has old wire
   bytes. Additive-only: never renumber, never change a field's type,
   never repurpose a tag.
2. **Two envelope shapes coexist and every sink must duck-type on
   `DESCRIPTOR`.** Proto `Event` messages (from `new_event` / the typed
   factories) and plain dicts (from `make_event`) both flow through the
   same `emit()` fan-out. This is a known, deliberately-kept wart (see
   `RATIONALE.md`); do not "fix" it by deleting `make_event`.
3. **Emission is observability, never control flow.** `emit()` collects
   per-sink exceptions with `return_exceptions=True` and logs them; a
   crashing sink can neither abort the run nor block other sinks. Every
   telemetry emit site wraps its own call in best-effort try/except.
   `asyncio.CancelledError` is the ONE exception that re-raises so task
   cancellation still propagates.
4. **Consumers join on string vocabularies you must not silently
   change.** `SteeringDecisionMade.outcome`, `JudgementEmitted.verdict_kind`,
   `TaskTransitioned.source`, `cancel_reason` prefixes, and detector
   names are wire contracts. Adding a value is fine (readers tolerate
   unknowns). Renaming an existing value is a breaking change requiring
   a coordinated consumer bump.
5. **`sequence` is monotonic and gap-free per `run_id`, starting at 0.**
   It is the ONLY ordering key. `emitted_at` is advisory wall-clock.
   Mint it via `Session.next_sequence()` / `next_sequence_and_event_id()`
   — never invent your own counter.
6. **`event_id` is globally unique and stable.** Format
   `{run_id}:{sequence}:{uuid4_short}`. It survives outer-session
   collapse (harmonograf#61) where two turns share a `session_id` and
   each restarts `sequence` at 0. Mint via `Session.next_event_id`.
7. **Determinism: the uuid4 suffix routes through
   `goldfive.runtime.seeded_uuid4`** so a `set_seed` harness produces
   byte-identical event streams. Do not call `uuid.uuid4()` directly at
   an emit site.

## 1. The `Event` envelope

Every event goldfive emits is a proto `Event` message defined at the top
of `proto/goldfive/v1/events.proto`. The envelope carries five common
fields and exactly one payload out of the `oneof`:

```proto
// proto/goldfive/v1/events.proto
message Event {
  string event_id = 1;                        // globally unique, UUIDv7-ish
  string run_id = 2;                          // owning Session.run_id
  uint64 sequence = 3;                        // per-run monotonic, gap-free, from 0
  google.protobuf.Timestamp emitted_at = 4;   // advisory wall clock
  string session_id = 5;                      // routing key for multiplexed streams

  oneof payload {
    RunStarted run_started = 10;
    // … 34 more variants, tags 11..44 …
    JudgementEmitted judgement_emitted = 44;
  }
}
```

### 1.1 The five envelope fields

| Field | Tag | Semantics | Who stamps it |
|---|---|---|---|
| `event_id` | 1 | `{run_id}:{sequence}:{uuid4_short}`. Globally unique. Never empty on the wire. | `new_event` (mints a fallback if the caller didn't pass one). |
| `run_id` | 2 | The `Session.run_id` this event belongs to. Same value from `RunStarted` to `RunCompleted`/`RunAborted`. | `new_event` from `Session.run_id`. |
| `sequence` | 3 | Per-run monotonic counter starting at 0, gap-free. THE ordering key. | `Session.next_sequence()`. |
| `emitted_at` | 4 | Wall-clock `Timestamp`. Advisory only — clocks are non-monotonic, use `sequence` for order. | `now_ts()` inside `new_event`. |
| `session_id` | 5 | Stable `Session.id` across every event one turn produces. Empty string means "route via the stream's Hello session" (pre-#155 behaviour). | Runner / Steerer / Executor emitters. |

### 1.2 `session_id` vs `run_id` — why both

Under the three-session-unification work (goldfive#161/#164)
`Runner(session_id=...)` pins `Session.run_id = session_id`, so today
`Event.run_id == Event.session_id` for runs that flow through an outer
session (adk-web, the harmonograf client, kikuchi). They are kept
distinct at the proto layer because:

- `run_id` is the logical run lineage (would survive conversation turns
  if we ever decouple them).
- `session_id` is the routing key a downstream sink multiplexes on when
  one client connection carries multiple goldfive sessions.

Both fields are always populated for goldfive-emitted events post-#155.
When you write a new emit site, thread `session_id=session.id` through so
harmonograf can route correctly. `DefaultSteerer._new_envelope` in
`goldfive/steerer.py` already does this:

```python
# goldfive/steerer.py — DefaultSteerer._new_envelope
def _new_envelope(self, session: Session) -> Any:
    from goldfive.events import new_event
    return new_event(session.run_id, session.next_sequence(), session_id=session.id)
```

### 1.3 Minting `sequence` and `event_id` atomically

`Session` (in `goldfive/types.py`) is the sole authority for both
counters. Three methods:

- `Session.next_sequence() -> int` — advances and returns the counter.
- `Session.next_event_id(sequence=None) -> str` — mints
  `{run_id}:{sequence}:{uuid4_short}`; if `sequence is None` it advances
  the counter itself.
- `Session.next_sequence_and_event_id() -> tuple[int, str]` — the atomic
  pair, and the pattern new emit sites SHOULD use so the envelope's
  `sequence` and `event_id` agree without a stashed local:

```python
# goldfive/types.py — Session.next_sequence_and_event_id
def next_sequence_and_event_id(self) -> tuple[int, str]:
    seq = self.next_sequence()
    return seq, self.next_event_id(seq)
```

The `event_id` uuid suffix routes through `goldfive.runtime.seeded_uuid4`
(see `new_event` in `events.py`, and `next_event_id` in `types.py`) so a
seeded determinism harness gets byte-identical ids. This is invariant 7 —
never `import uuid; uuid.uuid4()` at an emit site.

## 2. The DUAL-ENVELOPE reality (a kept wart)

goldfive emits TWO envelope shapes onto the same sink stream, and every
sink must tolerate both. This is documented and deliberately retained —
see `RATIONALE.md` §"Why `make_event` (dict) coexists with typed
factories (proto)".

### 2.1 The two shapes

**Proto envelope** — built by `new_event(...)` (then the caller assigns
the `oneof`) or by a typed factory like `drift_detected_event(...)`.
Requires the `proto` optional-dependency group. Has a `DESCRIPTOR`
attribute (every generated proto message does). This is the primary,
wire-stable, cross-language shape.

**Dict envelope** — built by `make_event(run_id, sequence, kind,
payload)`:

```python
# goldfive/events.py — make_event returns a plain dict
{
  "event_id": event_id or f"{run_id}:{sequence}:{seeded_uuid4().hex[:8]}",
  "run_id": run_id,
  "sequence": sequence,
  "session_id": session_id,
  "emitted_at": {"seconds": ..., "nanos": ...},
  "kind": kind,          # a bare string, e.g. "reasoning_judge_utility_summary"
  "payload": dict(payload or {}),
}
```

The dict path is an **escape hatch**: tests and lightweight callers that
don't want the `proto` extra installed can still emit, and it is the
only route for event kinds that have NO proto payload yet (the current
production example is `reasoning_judge_utility_summary`, emitted from
`DriftObserver._emit_verdict_utility_summary`).

### 2.2 `DESCRIPTOR` duck-typing — the rule every sink obeys

Sinks distinguish the two shapes with `hasattr(event, "DESCRIPTOR")`.
The canonical dispatch is in `JSONLPersistenceSink.emit`:

```python
# goldfive/sinks/persistence.py — JSONLPersistenceSink.emit
if hasattr(event, "DESCRIPTOR"):
    line = MessageToJson(event, sort_keys=True, indent=None)   # proto path
elif hasattr(event, "to_dict"):
    line = json.dumps(event.to_dict(), sort_keys=True)
elif isinstance(event, dict):
    line = json.dumps(event, sort_keys=True, default=str)      # dict path
else:
    payload = {k: v for k, v in vars(event).items() if not k.startswith("_")}
    line = json.dumps(payload, sort_keys=True, default=str)
```

`SQLitePersistenceSink._event_fields` has the same branch. `LoggingSink`
falls back to `repr(event)` on any serialisation failure so a malformed
event never silently drops.

### 2.3 The one sink that does NOT accept dicts: `GRPCSink`

`GRPCSink.emit` forwards proto only. Dict envelopes are dropped with a
debug log because the wire format is strictly proto:

```python
# goldfive/sinks/grpc_sink.py — GRPCSink.emit
if not hasattr(event, "DESCRIPTOR"):
    log.debug("GRPCSink: dropping non-proto event of type %r", type(event).__name__)
    return
```

**Consequence for you:** if you emit a new dict event via `make_event`
and it needs to reach an out-of-process observer over gRPC, it will NOT
arrive. Either give it a proto payload (preferred — see §8) or pair
`GRPCSink` with a dict-aware local sink (`JSONLPersistenceSink`). The
`reasoning_judge_utility_summary` summary event is JSONL/SQLite/in-memory
only for exactly this reason — it has no proto payload and gRPC drops it.

### 2.4 Why the wart is kept (do not delete `make_event`)

`RATIONALE.md` records the tradeoff. Removing the dict path would force
the `proto` extra on every test and lightweight tool. Issue #53 tracked
a real bug from mixing shapes incorrectly; the fix was careful sink
authoring (the `DESCRIPTOR` branch), NOT removing either path. The
signal that would justify consolidation is "downstream tooling uniformly
installs the proto extra AND `make_event` becomes dead" — that is not
true today (`make_event` is live for `reasoning_judge_utility_summary`
and several test scenarios).

## 4. `events.py` — factories and `emit()`

### 4.1 The three primitives

- `now_ts() -> Timestamp` — current wall clock as a
  `google.protobuf.Timestamp`. Raises `ModuleNotFoundError` if the
  `proto` extra is missing.
- `new_event(run_id, sequence, session_id="", *, event_id="") -> Event` —
  builds an envelope with `run_id` / `sequence` / `emitted_at` /
  `session_id` / `event_id` set. The caller assigns the `oneof` payload.
  If `event_id` is empty it mints `{run_id}:{sequence}:{seeded_uuid4}`.
- `make_event(run_id, sequence, kind, payload=None, *, session_id="",
  event_id="") -> dict` — the dict escape hatch (§2.1).

### 4.2 Typed factories — one per proto payload

Each factory calls `new_event`, sets its payload's fields, and returns
the envelope. Examples: `run_started_event`, `plan_revised_event`,
`task_completed_event`, `drift_detected_event`,
`steering_decision_made_event`, `policy_applied_event`,
`ladder_transition_decided_event`, `retry_budget_spent_event`,
`invocation_cancelled_event`, `task_transitioned_event`,
`task_transition_refused_event`, `delegation_observed_event`,
`invocation_boundary_entered_event` / `_exited_event`.

`drift_detected_event` is the one factory with real logic — it maps the
`DriftEvent` dataclass onto the proto, including enum-name normalisation
(`DriftKind.Value(...)`), the `authored_by` kind-based inference
fallback, and `annotation_id` extraction. Read it before emitting a
drift out-of-band:

```python
# goldfive/events.py — drift_detected_event (authored_by fallback excerpt)
authored_by = str(getattr(drift, "authored_by", "") or "").strip()
if not authored_by:
    kind_val = str(getattr(drift, "kind", "")).upper()
    is_user_kind = (
        kind_val.endswith("USER_STEER")
        or kind_val.endswith("USER_CANCEL")
        or kind_val.endswith("USER_PAUSE")
    )
    authored_by = "user" if is_user_kind else "goldfive"
evt.drift_detected.authored_by = authored_by
```

`build_plan_revision_diff(old_plan, new_plan) -> PlanRevisionDiff` is a
standalone helper (returns a bare `PlanRevisionDiff`, not an envelope) so
tests can splice a diff without constructing a full event. Task identity
is by `id`; edge identity is the `(from_task_id, to_task_id)` pair.

### 4.3 `emit()` semantics (post-#479)

`emit(sinks, event_pb)` fans one envelope out to every sink concurrently
and is the single point that enforces invariant 3:

```python
# goldfive/events.py — emit
async def emit(sinks: list[Any], event_pb: Any) -> None:
    if not sinks:
        return
    results = await asyncio.gather(
        *(sink.emit(event_pb) for sink in sinks),
        return_exceptions=True,
    )
    for sink, r in zip(sinks, results, strict=True):
        if isinstance(r, asyncio.CancelledError):
            raise r
        if isinstance(r, BaseException):
            log.exception(
                "sink %s.emit raised; event dropped for this sink only",
                type(sink).__name__,
                exc_info=r,
            )
```

Behaviour spec:

1. **Empty sink list is a no-op** — returns immediately.
2. **All sinks run concurrently** via `asyncio.gather`. One slow sink
   (e.g. a network `GRPCSink`) does not serialise the others.
3. **Log-and-continue.** A sink raising a normal exception is logged at
   `exception` level and the event is dropped FOR THAT SINK ONLY. Other
   sinks still observed it; the emitting run is unaffected. This is the
   #479 hardening — "sink exceptions never abort runs" — verified across
   the sink suite.
4. **`CancelledError` passthrough.** If a sink's coroutine was cancelled,
   `emit` re-raises it so cooperative cancellation still propagates up.
   This is the single exception to log-and-continue. Do not add a blanket
   `except BaseException` around `emit` at a call site that would swallow
   `CancelledError` — you would wedge the cancellation contract.

### 4.4 The steerer's emit shim

Steerer / observer emit sites route through `DefaultSteerer._new_envelope`
+ `_emit` (both in `steerer.py`), which are thin wrappers over `new_event`
and `emit`. The observer's decision-telemetry helpers (`_emit_steering_decision`,
`emit_no_drift_decision`, etc.) additionally wrap the factory import in
`except ModuleNotFoundError: return` so a proto-less smoke-test
environment degrades silently:

```python
# goldfive/drift_observer.py — _emit_steering_decision (guard excerpt)
try:
    from goldfive.events import steering_decision_made_event
except ModuleNotFoundError:  # pragma: no cover -- proto-less env
    return
```

## 5. Sink catalog

Five sinks ship in-box. All conform to the `EventSink` protocol pinned in
`goldfive/protocols.py`: `async emit(event)` + `async close()`. Only
`InMemorySink` is importable without the `proto` extra; the other four
guard their imports in `sinks/__init__.py` and expose `None` when `proto`
(or `grpcio` for `GRPCSink`) is missing.

### 5.1 `InMemorySink` (`memory.py`)

- **Format:** none — appends the raw event object (proto or dict) to a
  Python list, exposed via the `events` property.
- **Never raises.** The whole stream is retained (unbounded), so a
  long-running production caller will grow memory without a manual tail.
- **When to use:** tests (the list is the ground truth for assertions),
  and ephemeral callers that inspect the stream after a short run.
- **`close()` is a no-op** and keeps the list populated so post-run test
  assertions still work.

### 5.2 `LoggingSink` (`logging_sink.py`)

- **Format:** one JSON line per event via
  `MessageToJson(event, preserving_proto_field_name=True, indent=None)`
  — SNAKE_CASE keys (proto field names preserved). Newlines stripped so
  each event is exactly one log record.
- **Fallback:** `repr(event)` on any serialisation failure — never
  silently drops.
- **Accepts dicts?** It calls `MessageToJson` unconditionally; a dict
  would raise and fall to `repr`. In practice used on proto streams.
- **When to use:** dev tail on stdout/journald. Caller supplies the
  logger + level so formatting/handlers/filtering stay theirs.

### 5.3 `JSONLPersistenceSink` (`persistence.py`) — the zicato format

- **Format:** one JSON document per line via
  `MessageToJson(event, sort_keys=True, indent=None)`. Note: NO
  `preserving_proto_field_name` → the default is `False` → **camelCase
  keys**. This is the format zicato reads (canonical fact: "JSONL
  camelCase for zicato"). Contrast with `LoggingSink`'s snake_case.
- **Dict-aware:** the `DESCRIPTOR` branch (§2.2) means dict events (e.g.
  `reasoning_judge_utility_summary`) round-trip too, via
  `json.dumps(event, sort_keys=True, default=str)`.
- **Concurrency:** a single `asyncio.Lock` serialises writes so lines
  never interleave. Write is synchronous `write` + `flush` inside the
  lock; file opened lazily on first `emit`.
- **Replay:** `replay_from_jsonl(path) -> list[Event]` parses each line
  via `Parse` into a fresh `Event`; `reconstruct_session(events) ->
  Session` walks them and rebuilds a best-effort `Session` (latest plan
  wins; `dry_run` revisions skipped; unknown task ids ignored).
- **When to use:** crash recovery + resume, and the offline zicato
  meta-loop reading the camelCase JSONL.

### 5.4 `SQLitePersistenceSink` (`sqlite_sink.py`)

- **Format:** one row per event in table `goldfive_events` with PK
  `(run_id, sequence)`; columns `run_id`, `sequence`, `emitted_at` (ms),
  `kind` (the `WhichOneof("payload")` string), `payload_json`
  (`MessageToJson(sort_keys=True)` — also camelCase). `PRAGMA
  journal_mode=WAL`, autocommit (`isolation_level=None`).
- **Dict-aware** via the same `DESCRIPTOR` branch in `_event_fields`.
  For dict events `kind` comes from `data["kind"]`.
- **Cross-run query:** `list_runs(path)` (distinct run_ids ordered by
  first `rowid`), `replay_from_sqlite(path, run_id)` (rows for one run
  ordered by `sequence`, parsed via `Parse`).
- **Table name is templated, not bound** (SQLite can't parameterise
  identifiers) so `_validate_table` restricts it to `[A-Za-z_][A-Za-z0-9_]*`.
  Never pass a user string as `table` without going through that guard.
- **When to use:** dashboards / shared-DB integrations that query across
  runs. Trades a little replay fidelity for SQL queryability; can coexist
  with the JSONL sink on the same run.

### 5.5 `GRPCSink` (`grpc_sink.py`)

- **Format:** proto `Event` only — non-proto events dropped with a debug
  log (§2.3). Forwards each message over a client-streaming
  `StreamEvents` RPC to a `GoldfiveIngress` server.
- **Async-native, non-blocking:** `emit` enqueues on an `asyncio.Queue`
  and returns; a single background drain task pumps the queue into the
  stream. `close` pushes a sentinel, awaits the drain, closes the channel.
- **Reconnect:** on by default with bounded exponential backoff (0.5s →
  cap 5.0s). `max_queue=0` (default) is unbounded; a non-zero value
  back-pressures `emit`.
- **When to use:** streaming to an out-of-process observer (harmonograf's
  ingress). Pair with `JSONLPersistenceSink` if you also emit dict events.

### 5.6 Choosing a sink — reconciled with the code

| Need | Sink | Why |
|---|---|---|
| Test assertions on the stream | `InMemorySink` | List is ground truth; never raises. |
| Dev tail, human-readable, snake_case | `LoggingSink` | One JSON line, proto field names. |
| Crash recovery / resume; zicato offline read | `JSONLPersistenceSink` | Replayable + `reconstruct_session`; camelCase for zicato. |
| Cross-run SQL queries / dashboards | `SQLitePersistenceSink` | `(run_id, sequence)` PK; `list_runs` / `replay_from_sqlite`. |
| Live out-of-process observability (harmonograf) | `GRPCSink` | Streaming proto; reconnect + backpressure. Proto-only. |

The `VOCABULARY.md` §6 "Who each sink cares about" table says every sink
consumes "everything"; that is accurate for the four proto-aware sinks.
The one correction the CODE forces over the doc: `GRPCSink` will silently
skip dict envelopes (`make_event`), so "everything" for `GRPCSink` means
"every proto event". Trust the code.

### 5.7 Sink lifecycle — `close()` and lazy resource acquisition

Every sink implements `async close()` and every sink acquires its
resource LAZILY on first `emit`, so constructing a sink is side-effect
free and can happen off the event loop:

| Sink | `close()` does | Reopen after close? |
|---|---|---|
| `InMemorySink` | No-op; list stays populated for post-run inspection. | N/A (list persists). |
| `LoggingSink` | No-op; loggers own their handler lifecycle. | N/A. |
| `JSONLPersistenceSink` | Flush + close the file handle (idempotent). | Yes — next `emit` reopens. |
| `SQLitePersistenceSink` | Close the connection (idempotent). | Yes — next `emit` reopens. |
| `GRPCSink` | Push sentinel, await the drain task, close the channel. | No — `_closed` gates further emits (they drop with a debug log). |

Two lazy-init subtleties a weak model trips on:

1. **`asyncio.Lock` is created in `__init__` but binds to the running
   loop at first `await`.** `JSONLPersistenceSink` / `SQLitePersistenceSink`
   deliberately construct the lock eagerly and open the file/connection
   lazily so the sink can be built on one thread and attached to a loop
   later. Do not move the file open into `__init__`.
2. **The Runner owns sink teardown.** Executors call
   `drain_session_background_tasks` (which flushes the verdict-utility
   summary, §6.6) BEFORE the terminal `RunCompleted` / `RunAborted`, and
   the Runner calls `sink.close()` on each sink at Runner teardown. If you
   add a sink with buffered state, flush it in `close()`; the framework
   guarantees `close()` is called once per sink at the end.

## 6. Decision telemetry as a spec

Decision telemetry is the family of events that record what goldfive
*considered* and *decided*, not just what happened. zicato (the offline
meta-loop optimizer) reads these to tune detector thresholds and prompts;
harmonograf renders them on a dedicated "goldfive" lane. Getting the
vocabulary wrong silently breaks those consumers (invariant 4).

### 6.1 `SteeringDecisionMade` — the per-detector decision record

Emitted on EVERY detector evaluation, fire OR no-fire. Pairs with
`DriftDetected`: on a fire both events are on the wire with matching
`drift_id`; on a no-fire only `SteeringDecisionMade` emits. The negative
class (`outcome="no_drift"`) is the whole point — without it, "detector
quiet" is indistinguishable from "detector never ran".

**`outcome` vocabulary** (the join value consumers switch on):

| `outcome` | Meaning | Emitted from |
|---|---|---|
| `"no_drift"` | Detector ran, decided not to fire. Negative class. | `emit_no_drift_decision` |
| `"drift_emitted"` | Detector fired AND the steerer dispatched it. Paired `DriftDetected` on the wire. | `_emit_drift_detected` (default branch) |
| `"drift_suppressed"` | Detector fired but the steerer suppressed the dispatch (a fresher user-steer was active). Paired `DriftDetected` still emitted with `suppressed_by_user_steer=true`. | `_emit_drift_detected` (suppression branch) |
| `"drift_dropped_stale"` | Verdict landed against a plan revision the system has already moved past (the redundant-verdict watermark, `#480`). Observability-only; no cancel/refine. | `_handle_drift` redundant-verdict gate → `_emit_drift_detected(decision_outcome="drift_dropped_stale")` |
| `"drift_dropped_inflight"` | A concurrent refine for the same `(kind, target)` is already in flight (`#480`). Observability-only. | `_handle_drift` in-flight-key gate → `_emit_drift_detected(decision_outcome="drift_dropped_inflight")` |

**Full field table** (from `events.proto` and `steering_decision_made_event`):

| Field | Tag | Meaning |
|---|---|---|
| `detector_name` | 1 | Symbolic detector name (vocabulary below). |
| `outcome` | 2 | The five-value vocabulary in the table above. |
| `reason` | 3 | One-line human reason (`"cosine 0.42 below 0.6 healthy bound"`, `"observation_only=true"`). |
| `score` | 4 | Detector-specific scalar (cosine for reasoning, `count/threshold` for tool-loops). `0.0` when no single score summarises. |
| `considered_severity` | 5 | Severity the detector considered; `""` when no drift would fire. |
| `chosen_severity` | 6 | Severity the steerer applied; empty on `no_drift` AND on any non-`drift_emitted` outcome. |
| `considered_intervention_level` | 7 | Bare-lowercase `InterventionLevel` the detector/steerer considered. |
| `chosen_intervention_level` | 8 | Level actually applied; empty when no intervention fired. |
| `drift_id` | 9 | Cross-ref to the paired `DriftDetected.id` when `outcome != "no_drift"`; empty on the silent path. |
| `decided_at` | 10 | Advisory `Timestamp` stamped by `now_ts()` in the factory. |
| `invocation_id` | 11 | ADK invocation the decision concerns; empty for trajectory-level. |
| `task_id` | 12 | Task the decision is attributed to; empty when trajectory-level. |
| `agent_name` | 13 | Agent the decision is attributed to; empty when unbound. |

The stale/inflight outcomes (#480) exist so the optimizer's training set
distinguishes real fires from gate-dropped observations. The override
mechanism is the `decision_outcome` / `decision_reason` kwargs on
`_emit_drift_detected`:

```python
# goldfive/drift_observer.py — _handle_drift stale-verdict gate (excerpt)
self._verdict_ledger(session)["emitted_redundant"] += 1
await self._emit_drift_detected(
    session, drift,
    decision_outcome="drift_dropped_stale",
    decision_reason=(f"stale verdict: observed revision "
                     f"{drift.observed_revision_index} but same "
                     f"(kind, target) addressed at revision {last_addressed}"),
)
return
```

**`detector_name` vocabulary.** Stamped by `_detector_name_for_drift`: a
`detector_name` on the `DriftEvent` dataclass wins (needed because
tool-loops and the embedding detector both emit `LOOPING_REASONING`, per
#204), else `_DETECTOR_NAME_BY_KIND` maps the kind, else the bare
lowercase kind. Known values: `reasoning_judge`, `goal_drift_judge`,
`tool_loops`, `capability_check`, `confabulation_risk`, `reflective_check`,
`reasoning_loop_embedding`, `reasoning_cluster_embedding`,
`intent_divergence_embedding`, `plan_reconciler`, `human_intervention`,
`user_control`. The #480 negative-class fix added the
`capability_check` no_drift path so the capability detector's silent
runs are on the wire.

**`considered_*` vs `chosen_*`.** `considered_severity` /
`considered_intervention_level` are what the detector evaluated;
`chosen_severity` / `chosen_intervention_level` are what the steerer
applied after gating/ladder routing. `chosen_severity` stays EMPTY
whenever the drift was not actually applied (suppression AND gate drops)
— see the ternary in `_emit_drift_detected`:

```python
chosen_severity=(str(drift.severity) if outcome == "drift_emitted" else ""),
```

### 6.2 `TaskTransitioned.source` — the transition-attribution vocabulary

Every successful transition stamps a `source`. Readers MUST tolerate
unknown values (forward-compat). Defined values (from the proto comment
and `task_transitioned_event` docstring):

| `source` | When |
|---|---|
| `"llm_report"` | LLM `report_task_*` with an explicit `task_id`. |
| `"handler_default"` | LLM `report_task_*` where `task_id` resolved from the adapter pin. |
| `"supersedes_reroute"` | Report on a superseded task routed to the REPLACE-kind successor (#266). |
| `"plan_revision"` | Refine changed the task's status (FAILED on a loop, CANCELLED on supersede). |
| `"cancellation"` | Cooperative-cancellation cascade from a CRITICAL drift (#251 Stream C). |
| `"executor_dispatch"` | Executor framework auto-start (`ParallelDAGExecutor.run_one` flipping to RUNNING). |
| `"control_rewind"` | `REWIND_TO` control marking a task + downstream PENDING (`_control.py`). |
| `"other"` | Anything not matching a more specific source. |

### 6.3 `ReasoningJudgeInvoked` — the judge-call record

Emitted on EVERY reasoning-drift judge call regardless of verdict (both
on-task and off-task) so a Gantt can show every judge call, not just the
firing ones. Field spec (all populated on every emission; old events
deserialize to `""`/`0`):

| Field | Tag | Meaning |
|---|---|---|
| `subject_agent_id` | 3 | Agent whose reasoning was judged; empty when none active. |
| `model` | 4 | Judge model (verbatim to `call_llm`). |
| `elapsed_ms` | 5 | Wall-clock duration of the judge call, ms. Advisory. Feeds the `reasoning_judge_utility_summary` p50/p95 (§6.6). |
| `reasoning_input` | 6 | Chain-of-thought the judge saw; truncated to 4096 chars. |
| `raw_response` | 7 | Raw judge response before JSON parse; truncated to 2048. Populated even on plumbing failures so malformed output is diagnosable from the wire. |
| `on_task` | 8 | Legacy boolean projection: `true` iff `classification == "on_task"`. |
| `severity` | 9 | `"info"` / `"warning"` / `"critical"` when off-task, else `""`. |
| `reason` | 10 | Judge's one-sentence explanation. |
| `classification` | 11 | Three-state (#480 iter-10): `"on_task"` / `"justified_deviation"` / `"erroneous_deviation"` / `""` (quiet-fail sentinel). |
| `focused_task_id` | 12 | (#480) Plan-task the judge attributed the reasoning to; `""` when off-plan. |
| `focus_confidence` | 13 | (#480) Judge's certainty in that attribution, clamped `[0.0, 1.0]`. |
| `stated_intent` | 14 | (#480) Judge's one-sentence summary of what the agent says it is doing. |
| `provenance` | 15 | (#480) Justified-deviation provoking signal: `"tool_error"` / `"surprising_result"` / `"discovered_dependency"` / `"new_information"` / `""`. |

Fields 12-15 are the #480 attribution additions — they mirror
`ReasoningJudgeVerdict` (the in-process dataclass) so the wire carries
the judge's FULL verdict, not just the drift projection. `elapsed_ms`
(field 5) is the latency signal the utility summary aggregates.

### 6.4 `JudgementEmitted` — the pluggable-judge verdict surface (#437)

Emitted on every `Judge.evaluate` call that produced a populated verdict
(empty-default verdicts are treated as "no signal" and skipped). Built-in
drift detectors ALSO emit one (via `_emit_judgement_from_drift`) so the
judge-centric surface sees every drift verdict alongside operator-judge
verdicts.

**`verdict_kind` vocabulary** — selects which flavour fields the consumer
reads. The runtime picks the first populated flavour in order: drift,
rubric, boolean, numeric. Consumers MUST switch on `verdict_kind`, not
infer from field population.

| `verdict_kind` | Flavour fields | Notes |
|---|---|---|
| `"drift"` | `drift_kind`, `severity` | Also emits the legacy `DriftDetected` so pre-judges consumers keep working. |
| `"rubric"` | `rubric_score`, `rubric_dimensions` (map) | Domain-defined range; goldfive does not interpret. |
| `"boolean"` | `boolean_result` | Pass/fail. |
| `"numeric"` | `numeric_value`, `metric_name` | e.g. `metric_name="cost_usd"`. |

`judge_name` is the join key for per-judge time series. For built-in
drift-flavoured emissions it defaults to the drift kind's bare lowercase
string (`"reasoning_drift"`, `"goal_drift"`). The DOUBLE-EMIT GUARD in
`_emit_drift_detected` is load-bearing: a custom drift-flavoured Judge
already emits its own `JudgementEmitted` keyed on the judge's real
`name`, so the built-in pairing is skipped when
`drift._judge_emitted_judgement` is set — otherwise one signal would land
TWO `JudgementEmitted` events and break the "join on judge_name" contract:

```python
# goldfive/drift_observer.py — _emit_drift_detected (guard excerpt)
if not getattr(drift, "_judge_emitted_judgement", False):
    await self._emit_judgement_from_drift(session, drift)
```

`_emit_judgement_from_drift` is additionally gated on the steerer having
a non-empty `_judges` list, so bare `DefaultSteerer()` tests keep the
legacy single-event (`len(sink.events) == 1`) behaviour.

### 6.5 `DriftDetected` lifecycle fields + `DRIFT_LIFECYCLE_RESOLVED` (#486)

`DriftDetected` carries condition-lifecycle metadata (goldfive#271 PR1)
so multiple emits for one logical condition collapse:

- `condition_id` — stable identity for the drift CONDITION (a logical
  group), `sha1(f"{kind.value}|{task_id}|{agent_id}|{turn_id}")[:16]`. A
  new turn opens a fresh condition; same-turn re-emits for the same
  kind+task+agent collapse. DISTINCT from `id` (per-event identifier
  from #199). This is an exact-hash stable key — invariant 6-compliant.
- `lifecycle` — a `DriftLifecycle` enum (`types.proto`):
  `DRIFT_LIFECYCLE_UNSPECIFIED` (0, legacy/single-shot), `OPENED` (1),
  `ESCALATING` (2), `RESOLVED` (3), `HUMAN_INTERVENTION_REQUIRED` (4).
- `prev_severity` — only meaningful on `ESCALATING`; lets a sink render
  "bumped from INFO → WARNING" without remembering the prior emit.

**`DRIFT_LIFECYCLE_RESOLVED` semantics (#486).** A condition resolves
when it becomes moot, emitting a `DriftDetected(lifecycle=RESOLVED,
severity=INFO)` recovery marker via
`DriftObserver._emit_resolved_conditions`. Two triggers:

1. **Task-terminal transition** —
   `resolve_conditions_for_terminal_task(session, task_id, to_status)`:
   when a task goes terminal (COMPLETED / FAILED / CANCELLED / NOT_NEEDED),
   every condition still open against it is mooted (no further observation
   can escalate it). Without this the active-drift set grows monotonically
   per run and consumers never see an intervention succeed.
2. **On-task reasoning verdict** —
   `_resolve_conditions_on_on_task_verdict(session, agent_name)`: an
   on-task judge verdict resolves ONLY the kinds the reasoning pipeline
   can open (`_REASONING_PIPELINE_DRIFT_KINDS`) — deterministic-detector
   conditions (tool loops, task failures, plan divergence) keep their own
   lifecycle. Gated on the same late-verdict staleness check
   (`_invocation_target_gone`) as the drift side so a verdict landing
   after its invocation terminated cannot resolve a fresh condition.

Critically, `GOAL_DRIFT` resolves ONLY at task-terminal, never on an
on-task verdict (canonical fact). `_emit_resolved_conditions`
deliberately does NOT route through `_emit_drift_detected` — resolution
is not a detector decision, so there is NO paired `SteeringDecisionMade`
/ `JudgementEmitted` and NO `session.drift_events` append. It is pure
lifecycle telemetry: behaviour is identical under `observation_only`
True and False (nothing reads the result to make an intervention
decision).

### 6.6 `reasoning_judge_utility_summary` — the #483 dict event

This is the ONE production event with NO proto payload — emitted as a
`make_event` dict from `DriftObserver._emit_verdict_utility_summary`. It
is the teardown summary of the per-session verdict-utility ledger.

**The ledger** (`_verdict_ledgers`, keyed by session id, created lazily
on first increment) counts:

| Counter | Incremented when |
|---|---|
| `acted_on` | Reasoning-judge verdict dispatched into `handle_drift` (a real intervention path). |
| `emitted_late` | Verdict emitted-only because the originating invocation already terminated (`_is_late_drift_for_terminated_invocation`, goldfive#319). |
| `emitted_redundant` | Verdict dropped by the stale-watermark gate OR the in-flight-refine gate (both `#480`), emitted only for observability. |
| `parse_fail` | Judge LLM ran (`verdict.judge_ran`) but quiet-failed — empty `classification` (raised, non-JSON, missing keys). |

Plus a bounded `elapsed_ms` sample list (cap `_LEDGER_ELAPSED_SAMPLES_CAP
= 1024`). At drain the summary dict carries the four counters,
`judge_calls` (len of samples), and nearest-rank `elapsed_ms_p50` /
`elapsed_ms_p95`:

```python
# goldfive/drift_observer.py — _emit_verdict_utility_summary payload
payload = {
    "acted_on": int(ledger["acted_on"]),
    "emitted_late": int(ledger["emitted_late"]),
    "emitted_redundant": int(ledger["emitted_redundant"]),
    "parse_fail": int(ledger["parse_fail"]),
    "judge_calls": len(samples),
    "elapsed_ms_p50": _nearest_rank_percentile(samples, 0.5),
    "elapsed_ms_p95": _nearest_rank_percentile(samples, 0.95),
}
```

**Drain lifecycle.** `drain_session_background_tasks(session_id)` pops
and emits the summary at each run boundary (BEFORE the executor's
terminal `RunAborted` / `RunCompleted`, so it rides inside the run).
`shutdown()` is the process-teardown fallback that flushes any ledgers
whose sessions never hit a run-boundary drain (custom executors, aborted
loops). The pop makes repeat drains idempotent; a session with no judge
activity never created a ledger, so quiet runs emit nothing. The whole
emit is wrapped in `except Exception … log.warning` — observability only.

Because this event is a dict, `GRPCSink` DROPS it (§2.3). It reaches
`InMemorySink`, `LoggingSink`, `JSONLPersistenceSink`, and
`SQLitePersistenceSink` (where its `kind` column is
`"reasoning_judge_utility_summary"`). If a future need requires it
out-of-process over gRPC, that is the signal to promote it to a proto
payload (§8) — the same graduation path `InvocationCancelled` (#262) and
`TaskTransitionRefused` took.

### 6.7 The other three decision-telemetry events

- **`LadderTransitionDecided`** — emitted whenever the intervention
  ladder picks a level. `to_level` is the chosen bare-lowercase
  `InterventionLevel` (`observe` / `absorb` / `nudge` / `cancel_reinvoke`
  / `pause_escalate` / `terminate`). `from_level` is RESERVED and always
  `""` — the ladder is stateless per call (derives the level purely from
  `(kind, severity, occurrence_count)`), so there is no prior-level slot.
  Consumers reconstruct transitions by joining rows on `(drift_kind,
  task)` ordered by `sequence`; `reason` already distinguishes
  first-occurrence from repeat. See 09-steering-ladder-and-gates.md.
- **`DetectorDispatchOrdered`** — snapshots the detector dispatch order
  once per session (or per recomputation). `dispatch_order` is a repeated
  detector-name list; `reason` explains the ordering (e.g.
  `"reasoning_drift_mode=disabled excludes embedding detectors"`). The
  optimizer needs the snapshot rather than inferring "what runs when"
  from fire patterns.
- **`RetryBudgetSpent`** — emitted on each refine attempt (success OR
  failure). `operation` (`"refine"` / `"refine_user_steer"` /
  `"generate"` / `"plan_template_validate"`), `attempt` (1-indexed),
  `budget_remaining` (`0` == exhausted), `reason`. The budget is
  `LLMPlanner._max_refine_attempts` (default 2). See 10-planning-and-revision.md.

### 6.8 `PolicyApplied` — the catch-all steerer-policy record

Generic decision-telemetry for steerer `else-if` branches that are not a
`DriftDetected` and not a per-detector or per-drift event. `policy_name`
is a stable symbolic name; `outcome` is `"applied"` / `"skipped"` /
`"suppressed"` (free-form, readers tolerate unknowns). Known policy
names to preserve:

| `policy_name` | Fires when |
|---|---|
| `observation_only_gate` | An emit was gated because `observation_only=True`. |
| `supersession_integration` | The supersedes-integration `set_session_plan` path ran. |
| `user_steer_cooldown` | A user-steer cooldown suppressed a follow-up drift. |
| `same_turn_dedup` | A same-turn re-fire was skipped. |
| `refine_failure_threshold` | The refine-failure counter tripped. |

`PolicyApplied` is where the `observation_only_gate` / `suppressed`
patterns surface for the optimizer. When you add a new steerer policy
branch, emit a `PolicyApplied` with a fresh stable `policy_name` rather
than inventing a bespoke dict event.

### 6.9 Worked example — the emit fan-out for one firing drift

When a reasoning-drift judge fires and the steerer dispatches it, a
SINGLE logical event produces a CLUSTER of wire events, in this order,
all with monotonically-increasing `sequence`. Understanding the cluster
prevents double-counting in a consumer:

1. `DriftDetected` (`_emit_drift_detected`) — the drift itself, carrying
   `id`, `condition_id`, `lifecycle=OPENED` (or `ESCALATING`),
   `authored_by="goldfive"`.
2. `SteeringDecisionMade` (`_emit_steering_decision`) — paired,
   `outcome="drift_emitted"`, `drift_id` == the `DriftDetected.id` above,
   `detector_name="reasoning_judge"`.
3. `JudgementEmitted` (`_emit_judgement_from_drift`) — ONLY if the steerer
   has installed judges (the `wrap` surface installs the built-ins), and
   ONLY if `drift._judge_emitted_judgement` is not already set;
   `verdict_kind="drift"`, `judge_name` == the drift kind's lowercase
   string.
4. Later, if the refine succeeds: `PlanRevised` (`_emit_plan_revised`)
   with `trigger_event_id` == the `DriftDetected.id`, so a consumer joins
   steps 1 and 4 into one intervention row.

A consumer that counts "interventions" must key on `condition_id` /
`drift_id`, NOT count raw `DriftDetected` rows — a single condition emits
one row per observation (OPENED → ESCALATING → RESOLVED) and every
dropped/suppressed observation ALSO emits a `DriftDetected` (with the
matching `suppressed_*` flag or a `drift_dropped_*` decision outcome). The
whole point of `condition_id` (§6.5) is to collapse that fan-out.

On the SILENT path (judge ran, on-task verdict), only step 2 emits, with
`outcome="no_drift"` and empty `drift_id` — there is no `DriftDetected`,
no `JudgementEmitted`, no `PlanRevised`. That asymmetry is exactly why the
silent-path `SteeringDecisionMade` exists: without it "detector ran and
stayed quiet" is invisible.

### 6.10 `GoldfiveLLMCall{Start,End}` — internal-work spans

Every goldfive-internal `await call_llm(...)` site (planner refine /
generate, goal-drift classifier, reasoning judge, goal-derive, reflective
self-progress check) is wrapped in a `GoldfiveLLMCallStart` /
`GoldfiveLLMCallEnd` pair, paired by `span_id`. These make goldfive's own
LLM work — the 45s of `planner.refine` between two agent spans — visible
on harmonograf's "goldfive" lane instead of an unexplained gap.

- `name` distinguishes the call site: `"refine_steer"`, `"judge_goal_drift"`,
  `"plan_generate"`, `"goal_derive"`, `"reflective_check"`,
  `"judge_reasoning"`.
- `GoldfiveLLMCallEnd.status` is `"completed"` (await returned) or
  `"failed"` (raised); `error` carries the truncated diagnostic on
  failure. The End is emitted on BOTH paths so a span always closes —
  never render a permanently-open span.
- `input_preview` / `output_preview` (≤4096 chars) and `decision_summary`
  (≤512 chars, active-voice "what goldfive DID") are the Gantt tooltip
  material. `output_preview` and `decision_summary` are populated ONLY on
  End (the decision is not known at Start).
- `start_time_ns` / `end_time_ns` (from `time.time_ns()`) give duration
  without re-deriving from `emitted_at`.

Because these are proto payloads, they reach `GRPCSink` and harmonograf.
Do not confuse them with `ReasoningJudgeInvoked` (§6.3): the judge event
is the judge's VERDICT record (one event, no pairing), while
`GoldfiveLLMCall*` is the generic call-SPAN wrapper (a Start/End pair) —
a `judge_reasoning` span and its `ReasoningJudgeInvoked` verdict both fire
for one judge call.

## 7. `RunAborted` lineage encoding (#482)

`RunAborted.reason` is a free-text string, but goldfive uses conventional
prefixes so harmonograf's Trajectory view can classify aborts. Two layers
carry lineage:

### 7.1 The pause-escalation deadline abort

When a `pause_escalate` intervention's deadline
(`SteeringConfig.pause_escalate_deadline_s`, or the built-in 600s
TERMINATE fallback) expires with no operator action,
`_control.py:abort_expired_pause` cancels every non-terminal task and
raises `_ControlCancelled(reason)` where the reason encodes the
escalation lineage from the pause message payload:

```python
# goldfive/executors/_control.py — abort_expired_pause (excerpt)
drift_kind = str(payload.get("drift_kind", "") or "unknown")
ladder_level = str(payload.get("ladder_level", "") or "pause_escalate")
reason = (
    f"pause escalation deadline expired after {deadline_s:g}s with no "
    f"operator action (drift_kind={drift_kind}, ladder_level={ladder_level})"
)
```

Each cascaded CANCELLED transition additionally stamps
`cancel_reason=f"run_aborted:pause_escalate_deadline:{drift_kind}"` on
its `TaskCancelled` envelope.

### 7.2 The `cancel_reason` prefix vocabulary

`DefaultSteerer.transition(..., cancel_reason=...)` (goldfive#205) stamps
a structured reason on `TaskCancelled` / `TaskFailed`. Conventional
prefixes recognised by harmonograf:

| Prefix | Meaning |
|---|---|
| `upstream_failed:<task_id>` | Cascade from a failed/cancelled ancestor. |
| `superseded_by_revision:<task_id>` | Refine replaced this task. |
| `run_aborted:<abort_reason>` | fail_fast / validation / budget. |
| `user_cancel:<annotation_id>` | User-initiated CANCEL control. |
| `adk_cancellation:<invocation_id>` | ADK mid-invocation cancel. |
| `steerer_policy:<drift_kind>` | Steerer-imposed cancel via the intervention ladder. |

Sinks that don't know the format surface the raw string, so it is safe
to evolve the vocabulary WITHOUT a proto change (it is a string field,
not an enum). This is the correct pattern for "structured-but-evolving"
attribution: a free-text field with a documented prefix convention, never
a new enum that would force `make proto` on every extension.

## 8. Proto workflow — adding a field or a payload

This is the procedure. Cross-reference 16-recipes.md for the copy-paste
version; the rules here are the ones a wrong edit violates.

### 8.1 Adding a FIELD to an existing payload

1. **Pick a fresh, never-used tag number.** Look at the highest tag in
   the message and the `reserved` list. NEVER reuse a `reserved` tag
   (e.g. `DriftDetected` field 11 `synthetic` is reserved — using 11
   corrupts old wire bytes). Additive-only: proto3 makes new fields
   optional with a zero default, so old readers ignore them and old wire
   bytes still deserialize.
2. **Add the field in `proto/goldfive/v1/events.proto`** with a doc
   comment stating: the default's meaning for pre-field producers, the
   truncation convention if it's a preview string (`" … [truncated]"`),
   and whether readers must tolerate unknown values.
3. **Regenerate stubs:** `make proto` (runs `grpc_tools.protoc` with
   `--python_out --pyi_out --grpc_python_out` into `goldfive/pb/`). This
   rewrites `events_pb2.py`, `events_pb2.pyi`, `events_pb2_grpc.py`.
   NEVER hand-edit those files.
4. **Set the field at the emit site** — usually the typed factory in
   `events.py`. Guard optional fields with `if value:` so pre-field
   producers keep the same wire shape (see how `drift_detected_event`
   only sets `trigger_input` / `annotation_id` when non-empty).
5. **Consumers deserialize the new field to its zero default** — no
   consumer bump required for an additive field. If harmonograf/zicato
   need to READ it, that is a separate coordinated change.

### 8.2 Adding a NEW payload (a new `oneof` variant)

1. **Define the message** in `events.proto` and **add it to the `oneof`
   with a fresh tag** (next after 44). The message tags restart at 1
   inside the new message.
2. `make proto`.
3. **Add a typed factory** in `events.py` following the existing pattern:
   `new_event(...)` → set the payload's fields → return. Take
   `session_id` and `event_id` kwargs and thread them through.
4. **Emit via `emit(sinks, evt)`** wrapped in best-effort try/except at
   the call site (invariant 3). If the caller may run proto-less, guard
   the factory import (`except ModuleNotFoundError: return`).
5. **Every proto-aware sink handles it for free** — the `DESCRIPTOR`
   branch serialises any proto message; `WhichOneof("payload")` gives
   SQLite its `kind`. No sink edit needed. `GRPCSink` streams it once the
   ingress server knows the type.

### 8.3 `pb/` hygiene

- The generated `goldfive/pb/goldfive/v1/*_pb2.*` files ARE committed
  (they're imported lazily at runtime). After `make proto`, commit the
  regenerated stubs together with the `.proto` change in one commit.
- `events.py` and the sinks import the stubs LAZILY (inside functions,
  not at module top) so `import goldfive` works without the `proto`
  extra. Preserve that — do not hoist a `from goldfive.pb...` import to
  module scope.
- CI runs on the `proto` extra (`dev+adk+proto`); a stale `.pyi` or an
  ungenerated field will fail there. Run `make proto` locally and diff
  before pushing.

### 8.4 When to promote a dict event to proto

The graduation pattern (used by `InvocationCancelled` #262 and
`TaskTransitionRefused` #266→#267): ship a dict via `make_event` first to
keep a PR's scope tight and avoid proto-regen churn, THEN once the shape
has settled and a consumer needs cross-process/gRPC delivery, add the
proto payload + typed factory and migrate the emit site. Today
`reasoning_judge_utility_summary` is the one live dict event awaiting
this graduation if it ever needs gRPC reach.

## 9. What harmonograf and zicato consume

### 9.1 harmonograf (live observability UI, `GRPCSink`)

- Consumes the proto `Event` stream over gRPC. Routes each event to a
  session by `Event.session_id` (falling back to the stream's Hello
  session when empty) — the multiplexing reason `session_id` exists
  (§1.2). The harmonograf#61 session-rollup work stamps events onto the
  client's outer Hello session; `event_id`'s uuid suffix keeps the PK
  unique across that collapse.
- Renders `ReasoningJudgeInvoked`, `GoldfiveLLMCall{Start,End}`,
  `SteeringDecisionMade`, and resolved-condition `DriftDetected` on a
  dedicated "goldfive" lane keyed on the event kind (the compound
  `"<client>:goldfive"` synthetic agent).
- Uses `trigger_event_id` (on `PlanRevised`) ↔ `DriftDetected.id` /
  `annotation_id` strict matching to dedup an intervention into ONE row
  instead of three cards (annotation + drift + plan_revised).
- Reads `TaskTransitioned.source` and `cancel_reason` prefixes to
  colour-code the Trajectory view.
- Does NOT receive dict events (`reasoning_judge_utility_summary`) —
  `GRPCSink` drops them.

### 9.2 zicato (offline meta-loop optimizer)

- Reads goldfive's telemetry OFFLINE from the camelCase JSONL that
  `JSONLPersistenceSink` writes (canonical: "JSONL camelCase for
  zicato"). It ALSO reads `reasoning_judge_utility_summary` (a dict
  event) which reaches JSONL/SQLite but not gRPC — so JSONL is zicato's
  full-fidelity source.
- Consumes the silent-path telemetry (`SteeringDecisionMade` with
  `outcome="no_drift"` and the `drift_dropped_*` outcomes) as the
  negative-class training signal for threshold tuning. The
  `considered_*` / `chosen_*` split and `score` field are its features.
- Mutates goldfive knobs per `goldfive/optimization/manifest.toml` — the
  source-of-truth inventory of every prompt body and numeric threshold
  zicato may touch (each entry has a `source`, a `python_attr`, a
  numeric `range`, and `tags`). Adding a knob means an entry here PLUS a
  coverage row in `tests/test_optimization_manifest.py` (an AST-based
  test keeps the manifest's default in sync with the code). Do not let
  the manifest's notion of a default silently drift from the code.
- The `reasoning_judge_utility_summary` counters (`acted_on` vs
  `emitted_late` vs `emitted_redundant` vs `parse_fail`) plus p50/p95
  latency are zicato's signal for whether the judge is earning its cost.

## 10. Common mistakes

### 10.1 Emitting a new event kind as a bare dict when a proto payload exists or is warranted

**Wrong:** reaching for `make_event(run_id, seq, "my_new_thing", {...})`
because it is one line and skips `make proto`.

**Why it breaks:** `GRPCSink` DROPS dict events, so harmonograf never
sees it. The dict path is the escape hatch for the proto-less environment
and for genuinely-transient shapes — not a shortcut to avoid schema work.

**Correct:** if the event is a first-class signal a live observer should
see, add a proto payload + typed factory (§8.2). Reserve `make_event`
for the documented dict-only case (`reasoning_judge_utility_summary`) or
tests. If you must ship a dict first for scope reasons, follow the #262
graduation pattern and file the promotion.

### 10.2 Reusing a field number (or a reserved one)

**Wrong:** "field 11 on `DriftDetected` is free, I'll use it for my new
flag."

**Why it breaks:** 11 is `reserved` (the retired `synthetic` field, #271
Option A). Old wire bytes carrying field 11 would be misparsed as your
new field. Every consumer with historical data corrupts.

**Correct:** always take the NEXT unused tag. Check the highest tag in
the message AND the `reserved`/`reserved "name"` lines. Never renumber an
existing field, never change its type.

### 10.3 Changing an `outcome` / `verdict_kind` / `source` string consumers join on

**Wrong:** renaming `"drift_emitted"` to `"drift_fired"` because it reads
better, or "cleaning up" `"no_drift"` to `"none"`.

**Why it breaks:** zicato joins its training set on these exact strings;
harmonograf filters on them. A rename is a silent breaking change — no
type error, just a consumer that suddenly sees zero rows for the old
value.

**Correct:** ADD new values (readers tolerate unknowns per the "MUST
tolerate unknown" contract on every such field). Renaming an existing
value requires a coordinated consumer bump across harmonograf and zicato.
Same rule for `TaskTransitioned.source` and the `cancel_reason` prefixes.

### 10.4 Emitting in a hot path without the best-effort wrapper

**Wrong:**
```python
await emit(self._sinks, evt)   # unguarded, in a detector hot path
```

**Why it breaks:** a proto-less environment raises `ModuleNotFoundError`
on the factory import; a bug in a field assignment raises; and now your
detector — pure observability — has aborted the run. Invariant 3
violated.

**Correct:** wrap decision-telemetry emits the way the established
helpers do — guard the factory import (`except ModuleNotFoundError:
return`) and wrap the emit in `except Exception … log.warning`. Note
`emit()` itself already log-and-continues per-sink; the wrapper protects
against the FACTORY / field-assignment raising, which happens BEFORE
`emit`'s gather. Do NOT add a blanket `except BaseException` — that would
swallow `CancelledError` and break cancellation.

### 10.5 Inventing your own sequence or event_id

**Wrong:** `seq = self._my_counter; self._my_counter += 1` or
`event_id = str(uuid.uuid4())`.

**Why it breaks:** duplicate/gapped sequences break sink ordering
(invariant 5); a raw `uuid.uuid4()` breaks the seeded-determinism harness
(invariant 7) and drops the `{run_id}:{sequence}:` sortable prefix.

**Correct:** `seq, event_id = session.next_sequence_and_event_id()` and
pass both into the factory. The uuid suffix already routes through
`seeded_uuid4`.

### 10.6 Assuming JSONL and log lines have the same key casing

**Wrong:** writing a consumer that reads `drift_detected` from JSONL.

**Why it breaks:** `JSONLPersistenceSink` uses `MessageToJson` WITHOUT
`preserving_proto_field_name`, so JSONL keys are camelCase
(`driftDetected`). Only `LoggingSink` preserves snake_case
(`preserving_proto_field_name=True`). SQLite `payload_json` is also
camelCase.

**Correct:** zicato/JSONL consumers read camelCase; log-tail humans read
snake_case. Do not mix them up. If you need snake_case from JSONL, that
would be a producer change (and a break for zicato) — don't.

### 10.7 Routing a resolved-condition emit through the drift-decision path

**Wrong:** calling `_emit_drift_detected` to emit a
`DRIFT_LIFECYCLE_RESOLVED` marker.

**Why it breaks:** `_emit_drift_detected` pairs a `SteeringDecisionMade`
and a `JudgementEmitted` and appends to `session.drift_events` — a
resolution is NOT a detector decision, so all three are wrong. You'd
manufacture a phantom "drift_emitted" decision and inflate the drift
summary.

**Correct:** use `_emit_resolved_conditions` (§6.5), which emits a bare
`DriftDetected(lifecycle=RESOLVED, severity=INFO)` with `prev_severity`
and no paired decision/judgement events.

### 10.8 Deleting `make_event` or "consolidating" the two envelopes

**Wrong:** "there's a proto payload for almost everything now, let me
delete the dict path."

**Why it breaks:** `reasoning_judge_utility_summary` is live on the dict
path, tests use it, and it lets `import goldfive` work without the
`proto` extra. This is a KEEP decision documented in `RATIONALE.md`.

**Correct:** leave it. The signal that would justify consolidation
("downstream uniformly installs proto AND `make_event` is dead") is not
true today.
